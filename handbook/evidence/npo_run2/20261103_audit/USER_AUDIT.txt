2. The most important training issue: retain sampling
I found one significant deviation that deserves attention.

The code creates RETAIN_PAIRS once, before training. Each of the 200 forget examples receives one deterministic retain example. That mapping is then reused throughout all 62 updates.

The resulting selection contains only 195 distinct retain rows out of the 3,800 available—about 5.1% of the retain training set. The same small group is repeatedly used across the ten nominal passes.

This is not the same as repeatedly drawing a fresh random set of retain examples from the full retain set throughout training.

Why this matters:
- The retain objective is supposed to preserve a broad portion of the model's non-forget behaviour.
- Reusing the same 195 examples can encourage the model to fit those particular retained responses rather than preserve the wider retain distribution.
- The evaluation then tests 300 retained diagnostic questions, which are not limited to those 195 training examples.
This is a plausible contributor to the large retained-set performance drop in your results. I cannot prove it caused that drop without a comparison run, but it is a concrete sampling limitation—not speculation about the model's size.

The original TOFU training methodology describes randomly sampling retain examples while using the forget set as the anchor. Your code's one-time fixed pairing is therefore a meaningful implementation difference. 

My recommendation: in the corrected run, resample the retain examples across epochs or training updates using a reproducible sampler, rather than creating one fixed mapping for the entire experiment.

There is a second, smaller evaluation-sampling issue: the notebook selects the first 300 eligible retain diagnostic examples. It should ideally select a seeded random sample of 300 from the 400 eligible examples, then freeze that selection across all model conditions. The existing selection is still useful for paired comparisons, but the first 300 may not be representative of the whole diagnostic set.

A correction to the metric guidance I gave you earlier
I need to correct one technical detail from my earlier explanation of the evaluation formula.

TOFU's original Forget Quality uses a Truth Ratio based on the geometric mean of the perturbed-answer probabilities relative to the paraphrased correct-answer probability, followed by a KS comparison against the retain-only reference. The TOFU Model Utility implementation uses an arithmetic mean of the perturbed-answer probabilities for its truth-ratio component. These are different calculations serving different parts of the evaluator. 

GitHub+2

Your notebook stores both variants:
- source_geometric_truth_ratio_log: the appropriate geometric-based quantity for the Forget Quality KS comparison. Its orientation is the reciprocal of the paper's ratio, but a common monotonic reciprocal transformation does not change the two-sample KS statistic or p-value.
- arithmetic_truth_ratio_log: the arithmetic-based quantity used for the Model Utility truth-ratio component.
Therefore, the notebook's utility_arithmetic is the correct aggregate Model Utility to report, while utility_source_geometric is an additional sensitivity calculation.

However, I found a specific inconsistency in the comparison code: the matched_precision_KS calculation uses arithmetic_truth_ratio_log. It should use source_geometric_truth_ratio_log to remain consistent with the original Forget Quality definition. This can be corrected from the existing per-question CSVs; no model retraining or inference is required.

That correction matters because you need to compare:

NPO_{\mathrm{NF4}}
\quad\text{against}\quad
Retain95_{\mathrm{NF4}}

5.3 Why might this particular NPO checkpoint resist recovery?
I see four plausible explanations, ranked by how directly the current evidence supports them.

First: the target-answer signal is already very weak.

NPO has driven Forget05 gold-answer probability from 0.87802 to 0.11393. The retain-only oracle is at 0.12969. The unlearned model is already very close to the oracle under these measures, even slightly below it on gold-answer likelihood.

There may simply be little remaining correct-answer preference for NF4 to restore.

Second: this is full-weight NPO, not a small adapter update.

The notebook trains all model parameters, rather than learning a small LoRA update. The custom optimiser also maintains FP32 master weights for the BF16 model parameters.

That can produce a different update geometry from adapter-based or more constrained unlearning methods. It is possible that the updates in this run moved enough relevant parameters across the NF4 quantisation boundaries to survive conversion.

But this is still a hypothesis. The engineer has not exported a parameter-delta or quantisation-bin-crossing analysis, so we cannot establish that mechanism from the current results.

Third: the particular NF4 implementation and 1B model may be less susceptible under these conditions.

Quantisation-recovery outcomes depend on the model, unlearning method, update structure, quantiser, scaling and deployment path. The QRA paper's reported increase in recovered knowledge—from an average of 21% in full precision to 83% after 4-bit quantisation—comes from its evaluated models and methods; it is not a law that every INT4 conversion must reverse every unlearning intervention.

8. The QRA implementation: what is valid and what needs correction?
Your QRA test is valid as a first post-training quantisation probe:
\[
M_u^{\mathrm{BF16}}
\longrightarrow
\begin{cases}
Q_8(M_u)\\
Q_{\mathrm{NF4}}(M_u)
\end{cases}
\]

It uses real weight conversion, then evaluates the resulting quantised models. That is the right broad experimental order for testing whether ordinary deployment quantisation weakens an unlearning intervention.

However, its numerical interpretation needs two corrections.
Correction A: use the same-precision retain oracle
For an INT4/NF4 comparison, the cleanest TOFU comparison is:
\[
FQ_{\mathrm{NF4}} =
KS\left(
TR(Q_{\mathrm{NF4}}(M_u)),
TR(Q_{\mathrm{NF4}}(M_r))
\right)
\]

The retain-only oracle should undergo the same quantisation transformation as the unlearned model. Otherwise, you are comparing two precision states that may have different quantisation effects.

The notebook has already generated retain95_int8 and retain95_nf4, so the data needed for this comparison exists.

The current bootstrap code tests changes in:
